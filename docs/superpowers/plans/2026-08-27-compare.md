# Compare Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Hold the graded picture up against the ungraded one, on macOS — as a wipe or side by side.

**Architecture:** The engine composites the two *pictures*, because it owns the textures and presents to the layer itself; Swift draws the chrome over the top — the seam, the labels — the way the crop overlay already sits over the viewer. That split is also what makes this testable without a screen: `render_offscreen` returns the composited pixels.

**Tech Stack:** Rust, wgpu, the `pe-ffi` C ABI, Swift 6 / SwiftUI, XCTest.

**Predecessors:** batch export. This is the last large feature the Windows shell has and the Mac does not.

---

## Why both modes exist

`main.rs` argues it, and the argument decides the shapes:

> A wipe is for "did that move go too far" — the eye reads a discontinuity
> across a seam far more finely than it reads two pictures a hand's width apart.
> Side by side is for "which of these do I prefer", where a seam would fuse the
> two into one image and stop you seeing either.

So a wipe must have **no gap and no scaling difference** between the halves —
they are one picture with a seam — and side by side must have a real gap.

Off is in the cycle rather than being a separate way out: a comparison you
cannot turn off with the button that turned it on is a control that only works
in one direction.

## What the "before" is

The **working texture** — the frame after crop and geometry, before any effect —
through the display transform. One extra pass, no effects. `preview.rs` says it
is cheap enough not to bother caching and skipped entirely when nothing is
comparing; both remain true here.

It is emphatically *not* the file re-decoded. The comparison is "what did my
grade do", not "what did the crop do".

## Why this is testable after all

I said compare needed a working screen. That was half wrong. The presentation
does — but the compositing is the hard part, it happens inside the session, and
`Session::render_offscreen` hands back the pixels. A wipe at 0.5 over a
photograph with a visible edit must have the ungraded frame on the left and the
graded one on the right, and that is an assertion about bytes.

What still needs eyes: the seam's weight, the labels, and whether dragging the
wipe feels right.

## Task 1: The engine composites

**Files:**
- Modify: `crates/pe-render/src/transform.rs`, `crates/pe-session/src/session.rs`

- [ ] **Step 1: A pass that can draw into part of its target**

`TransformPass::encode` draws a full-screen quad. Both modes need less than the
whole target:

- **wipe** — the after frame drawn whole, then the before frame drawn whole and
  **scissored** to the left `wipe` fraction. One seam, no gap, no scaling
  difference, which is the entire point of a wipe.
- **side** — each frame drawn into half the target, so both fit where one did.
  That is a **viewport**, not a scissor.

wgpu render passes have `set_viewport` and `set_scissor_rect`, so neither needs
a shader change. Add one optional region parameter rather than two entry points
if that reads better; say which you did.

**A zero-width scissor or viewport is a validation error in wgpu, not a no-op.**
A wipe at 0.0 is a legitimate thing for a user to drag to. Handle it.

- [ ] **Step 2: The session**

```rust
#[derive(Clone, Copy, PartialEq, Eq, Debug, Default)]
pub enum Compare { #[default] Off, Wipe, Side }

impl Compare {
    /// The next mode round, so one button can be the whole control.
    pub fn next(self) -> Self
}
```

and `Session::set_compare(mode, wipe)`, `Session::compare()`.

Rendering the before frame is one `to_display` pass from the working texture
and is **skipped entirely when the mode is Off** — a comparison nobody asked
for should cost nothing.

Side by side clears to the viewer surround first, or the full-size after frame
shows behind the two halves.

- [ ] **Step 3: Tests, through `render_offscreen`**

This is why the feature is doable now. Give the photograph an edit that is
obvious in bytes — a large exposure shift — and read the pixels back.

```rust
    #[test]
    fn a_wipe_shows_the_ungraded_frame_on_the_left_and_the_graded_one_on_the_right() { }

    /// And the seam moves when the wipe does.
    #[test]
    fn the_seam_sits_where_the_wipe_says() { }

    /// At either end a wipe is all of one picture, and neither end is a
    /// validation error.
    #[test]
    fn a_wipe_at_nothing_is_the_graded_frame_and_at_everything_is_the_ungraded_one() { }

    #[test]
    fn side_by_side_puts_a_gap_between_two_half_size_pictures() { }

    /// Off costs nothing: the before pass does not run.
    #[test]
    fn comparing_nothing_renders_exactly_what_it_did_before() { }

    /// The before is the frame before the *effects*, not before the crop.
    #[test]
    fn the_ungraded_half_is_still_cropped() { }

    #[test]
    fn the_cycle_comes_back_to_off() { }
```

`the_ungraded_half_is_still_cropped` is the one that catches the tempting wrong
implementation — re-decoding the file — which would show the whole frame on one
side of the seam and the crop on the other.

## Task 2: The mode crosses

**Files:**
- Modify: `crates/pe-ffi/src/lib.rs`

```rust
pe_session_set_compare(s, mode: u32, wipe: f32) -> i32
pe_session_compare(s, out_mode: *mut u32, out_wipe: *mut f32) -> i32
```

`mode` as a small integer with the values written down on the function — 0 off,
1 wipe, 2 side — and an unknown value refused rather than silently treated as
off. Follow the sentinel rule: `-1` never reached the session, `-2` the session
refused.

Test through the ABI and assert on rendered pixels, not only return codes.
