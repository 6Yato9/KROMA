## Why a control needs the picture behind it

A curve editor with nothing behind it is a diagram of a function. You can see
the shape you have drawn and not the thing you drew it for. Every peak in the
histogram is a tone the photograph actually has, and moving the curve *there*
rather than a third of the way along is the entire difference between grading
and guessing.

`ColourSpread`'s own doc puts the sharp version of it: *drawing a tone histogram
behind a Hue Vs Sat curve would put every peak in the wrong place, which is
worse than drawing nothing.* A background that is wrong is not a cosmetic
failure — it aims the user at colours that are not there.

## The bug that is exactly that

`spread_behind` in `apps/windows/src/curve.rs` picks the hue bins when
`mode.x_is_hue()` and the saturation bins otherwise. There are seven modes:

| mode | x axis | gets today | wants |
|---|---|---|---|
| `Custom` | level | tone histogram | ✓ |
| `HueVsHue`, `HueVsSat`, `HueVsLum` | hue | hue spread | ✓ |
| `SatVsSat`, `SatVsLum` | saturation | saturation spread | ✓ |
| **`LumVsSat`** | **luminance** | **saturation spread** | **luma** |

`Mode::LumVsSat`'s own readout labels say `("Input Lum", "Saturation", …)`, and
neither `x_is_hue()` nor `x_is_saturation()` matches it — so it falls through
the `else` and gets saturation. Its background counts a quantity its x-axis is
not measuring. Every peak is in the wrong place, which is the failure
`ColourSpread` warns about, in the one mode nobody checked.

## Two numbers written three times

Where diffuse black and white sit in the curve's log domain appear as:

- `shaders/common.wgsl:134,136` — `CCT_BLACK`, `CCT_WHITE`
- `crates/pe-core/src/parametric.rs:88` — as a subtraction, `SDR_SPAN_IN_LOG`
- `apps/windows/src/curve.rs:29,30` — `LOG_BLACK`, `LOG_WHITE`

Swift is about to need them as a fourth. They go in `pe-core` beside
`SDR_SPAN_IN_LOG`, which then derives from them, and the shell stops declaring
its own.

**They matter more than a shared constant usually does.** The curve's plot spans
black to diffuse white, not the whole log domain, so the histogram's bins are
read *through that window* rather than laid out edge to edge — the Windows
comment says drawing them straight across "would put every tone about a seventh
of the plot to the left of where the curve acts on it". A seventh is not
subtle.

## Scope

The curve editor's backdrop and the warper's three clouds, on macOS, plus the
`LumVsSat` fix which lands on both shells. **Not** the spectral locus on the
chromaticity plot — that is a drawing of the visible gamut, not a measurement,
and the Windows `locus` module is a separate body of work with no Mac
equivalent yet.

```rust
//! Which measurement belongs behind which control.
//!
//! A curve editor with nothing behind it is a diagram of a function: you can
//! see the shape you drew and not the thing you drew it for. What goes behind
//! it has to be counted in the same units its x-axis is indexed by — a tone
//! histogram behind a Hue Vs Sat curve puts every peak in the wrong place,
//! which is worse than drawing nothing, because it aims the user at colours
//! that are not there.
//!
//! Shared rather than written per shell because it is the same question in
//! both, and because the mode that got it wrong got it wrong in the one shell
//! that had an answer at all.

/// What a control wants drawn behind it.
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum Backdrop {
    /// The three channel histograms, read through the SDR window.
    Tones,
    /// The luma histogram alone, for a curve indexed by luminance.
    Luma,
    /// Hue counts, running once round the circle from red.
    Hue,
    /// Saturation counts.
    Saturation,
    /// Nothing is known to belong there.
    Nothing,
}

impl Backdrop {
    /// What belongs behind the curve at `key`.
    ///
    /// Decided by what the curve's x-axis is indexed by, which is not always
    /// what its name leads with: `lum_vs_sat` reads an input *luminance* and
    /// outputs a saturation, so it takes a luma backdrop and not a saturation
    /// one.
    pub fn behind(key: &str) -> Self {
        match key {
            "luma" | "red" | "green" | "blue" => Backdrop::Tones,
            "hue_vs_hue" | "hue_vs_sat" | "hue_vs_lum" => Backdrop::Hue,
            "sat_vs_sat" | "sat_vs_lum" => Backdrop::Saturation,
            "lum_vs_sat" => Backdrop::Luma,
            _ => Backdrop::Nothing,
        }
    }
}
```

Add `pub mod backdrop;` to `crates/pe-scopes/src/lib.rs`, following how
`waveform` and `warper` are exposed.

## Task 2: The trace, shared and mirrored

A histogram of a photograph is spiky — real images have runs of identical
values, and every one of them is a bin standing alone. Drawn raw that reads as a
bar chart, which is a picture of the sampling rather than of the photograph.
Smoothing it is what turns it back into the curve it was measured from.

That smoothing lives in `apps/windows/src/curve.rs` as `trace`, in a binary
crate a fixture cannot reach. It moves to `pe-scopes` for the reason `home_of`
and the plot range moved before it: Swift needs the same arithmetic, and the way
to stop two copies drifting is to generate one from the other.

## Task 3: The picture behind the curve

**Files:**
- Modify: `apps/apple/KromaKit/Controls/CurveEditor.swift`

- [ ] **Step 1: Draw it**

`CurveEditor` already draws a grid, an identity line, the curve and its
handles, in that order. The backdrop goes **first**, under all of them.

- **`.tones`** — three filled areas, one per channel, each with a line along
  its top. The fills are **added, not blended**. Three translucent layers
  painted in order leave the last one on top, so a neutral picture — where all
  three channels agree — comes out whichever colour is drawn last. Adding makes
  agreement read as grey and disagreement as the colour in excess, which is the
  whole reason for overlaying them. In SwiftUI that is `.blendMode(.plusLighter)`
  on the fills.
- **`.luma`** — the luma plane alone, one translucent grey fill and a pale line.
- **`.hue`** / **`.saturation`** — the matching spread plane, drawn the same way
  as `.luma`.
- **`.nothing`** — nothing, silently. A curve with no known backdrop is not an
  error.

Heights run to about 92% of the plot so a full-height peak does not touch the
top edge and read as clipped when it is not.

Tone backdrops read their bins **through the SDR window**; spreads read edge to
edge. `CurveBackdrop`'s two lookups are that difference.

The counts come from `store.scopes` — `logHistogram` for `.tones` and `.luma`,
`colour` for `.hue` and `.saturation`. **When `scopes` is nil, draw nothing and
do not ask for a measurement here**: the editor is not the thing that decides
when to measure, and a view that triggered a full render plus readback from its
own body would do it on every layout pass.

## Task 4: The cloud behind the warper

**Files:**
- Modify: `apps/apple/KromaKit/Controls/WarpEditor.swift`, `PinsEditor.swift`

- [ ] **Step 1: Draw the haze**

`Scopes.WarperClouds` carries three 128 × 128 planes — `chromaticity`,
`hueSat`, `chromaLuma` — one per view, because the three views are three
different projections and a cloud measured for one is meaningless on another.

Three rules, all from the Windows `plot_image`:

- **Blur it first.** A frame's colours are a *sample* of a continuous
  distribution, and at this grid most cells hold nothing or one. Reading between
  them bilinearly still shows the lattice, because the lattice is genuinely what
  the counts look like. The Windows shell uses a separable 5-tap binomial —
  `[1, 4, 6, 4, 1] / 16` — which is near enough a Gaussian at this size and
  costs two multiply-adds a cell instead of twenty-five.
- **Then a fourth root**, normalised against the blurred peak: `pow(t, 0.25)`,
  scaled to about 0.85. A photograph's colours are wildly unevenly distributed —
  a sky is thousands of pixels in a handful of cells and a red jacket is a
  hundred over dozens. On a linear scale the jacket is invisible, and seeing
  the jacket is the entire point.
- **Add it to the space beneath**, do not draw it over. The haze brightens the
  plot's own colours where the photograph has them.

As with the scopes, build a `CGImage` once per generation rather than emitting
16,384 rectangles.

**The grids are read at plot fractions in each view's own terms.** The
chromaticity grid is binned with `pe_core::pins::plot_fraction`, which is the
same mapping `PinGeometry` uses — so the cloud and the pins agree, which they
did not before the scopes plan. The hue-sat grid is stored in the **square**
containing the unit disc, `−1…1` mapped to `0…1` on each axis, which is *not*
`WarpGeometry`'s polar mapping: convert through the square. Getting that wrong
puts the cloud on the right plot in the wrong place, which is the failure this
whole plan is about.

- [ ] **Step 2: Test the mapping, not the look**

The square-to-disc conversion for the hue-sat cloud is the piece that will be
wrong if anything is. Test it directly: a count at the square's centre must
